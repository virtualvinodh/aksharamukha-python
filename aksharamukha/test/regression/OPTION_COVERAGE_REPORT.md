# PostProcess / PreProcess option test coverage report

Generated by combining three independent signal sources per option: the real
frontend UI tooltip examples (`frontend_backend_manifest.json`), AST/regex
extraction of each function's own trigger logic (with corpus-first example
search against the heart/lalitavistara sample texts, falling back to a
synthetic minimal match via `sre_parse`), and multi-trigger enumeration
(every independently-resolvable `.replace()`/`.sub()` call site in a
function, not just the first). Every case below was re-verified by actually
calling the real function and checking the result, right before this report
was written - nothing here is guessed.

All resolved cases are already merged into `test_direct_options.json`
(post-options) and either `test_direct_options.json` or the hand-curated
`test_texts/test_postoptions.json` (pre-options are exclusively in
`test_direct_options.json` for now). This file documents what's *not* yet
covered, and why, so the gaps are legible instead of silent.

"Confirmed stub" = the function's body has no `.replace()`/`.sub()` call and
no delegation to another function that does - verified by AST inspection,
not by guessing from the name. Two flavors are split out below because
they mean different things: most are just unimplemented placeholders, but
a few have a **frontend UI tooltip describing a worked example for a
feature that doesn't exist in the code** - those are real product gaps,
not test-generation gaps.

### Problematic — 10 (no test data yet, with why)

| Option | Why |
|---|---|
| `RetainGurmukhiNumerals`, `RetainKannadaNumerals`, `RetainMalayalamNumerals`, `RetainTamilNumerals`, `RetainTeluguNumerals` | All delegate to `RetainIndicNumerals`, whose numeral-substitution regex also fires on the generic probe string used to check "does this trigger fire too broadly" (the probe happens to contain digits) - an artifact of the probe choice, not a real problem with the functions. | `TaiThamMoveNnga` | **Confirmed real bug**, not a coverage gap: computes a real substitution via `re.sub`, then discards it and returns the literal string `"Vinodh"` instead (`PostProcess.py:3467-3470`). | `removeSegmentSpacesBurmese` | Regex uses `\p{L}\p{M}*` - Unicode-property syntax Python's built-in `re` module doesn't support at all. This function likely doesn't work as documented in production either; a real bug, not a generation gap. |
| `urduRemoveInherent` | Needs more surrounding context (word-boundary conditions) than any generated candidate could satisfy in isolation - the isolated trigger never actually fires. |
